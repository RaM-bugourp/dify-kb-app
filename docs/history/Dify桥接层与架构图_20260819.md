# Dify RAG 桥接层 + 架构图

## 需求
老板确认：后台分区可以对接 Dify 做 RAG（Dify 只做文档向量化入库，图片存不了、只能转码）。要求：
1. 设计「分区 ↔ Dify 知识库」映射 + 对接层
2. 生成一份 mermaid 深色渲染架构图

## 结论要点
- Dify 本质是「文本→分段→embedding→向量检索」语义检索引擎，不是通用数据库
- 结构化数据（术语表/接口清单）Dify 做不了字段精确查询，图片原图 Dify 不存
- 因此架构天然是**混合**：结构化数据走 store.js（→MySQL），图片走 server/media，文档向量化走 Dify

## 改动清单

### 1. server/store.js（数据模型 + 函数）
- seed 新增 `difyMappings` 数组（分区 id ↔ Dify 知识库 id 映射，含 status/syncedAt）
- 新增函数：`setDifyMapping` / `getDifyMapping` / `getDifyMappingByDataset` / `listDifyMappings` / `removeDifyMapping`
- `deleteDataset` / `deleteFolder` 增加级联清理孤儿映射

### 2. server/dify-bridge.js（新建，RAG 桥接层）
- 接口签名对齐 Dify 官方 REST API（Dataset 生命周期 / 文档入库 / 检索）
- `USE_REAL_DIFY=true` 时 fetch 调用真实 Dify，否则 mock（本地分段 + 关键词打分）
- `ensureDatasetForFolder`：为分区创建/复用 Dify 知识库并记录映射
- `indexDocument`：文档文本切段（chunkText）→ 入库（真实走 create_by_text，mock 存内存）
- `retrieval`：语义检索（真实走 hybrid_search，mock 关键词打分）
- `status` / `listMappings` / `getMapping`：映射查询

### 3. server/index.js（路由 + wrap 支持 async）
- 新增 `/api/dify/*` 路由：status / mappings / folders/:id/dataset / documents / retrieval
- `wrap` 错误处理改为支持 Promise（async handler）

### 4. docs/architecture.mmd + architecture.svg（架构图）
- mermaid 深色主题（`%%{init:{'theme':'dark'}}%%`），6 个分组：前端/后端/本地存储/预留扩展/外部 Dify
- 类样式区分：core(蓝)/future(绿)/external(紫)
- 实线 = 当前链路，虚线 = 未来切换

## 验证结果（实测）
- `GET /api/dify/status` → mode=mock, mappings 含 f_arch
- `POST /api/dify/folders/f_terms/dataset` → 创建映射 dify_f_terms
- `POST /api/dify/documents`（中文文本入库）→ status=completed, segmentCount=1
- `POST /api/dify/retrieval`（query 向量化）→ 返回相关分段 score=2
- 全链路：建库→入库→检索 通
- 架构图 SVG 生成成功，中文正常（解决 UTF-8/GBK 乱码）

## 关键坑
1. **mermaid-cli 中文乱码**：mmdc 读 .mmd 用系统 GBK，中文变 `鍚戦噺搴?`；
   解法：给 .mmd 加 UTF-8 BOM，强制 Node 按 UTF-8 读
2. **mmdc 缺 chrome**：默认找 chrome-headless-shell，用 `-p puppeteer-config.json` 指定系统 Edge 可执行文件绕过
3. **PowerShell 执行策略**：`mmdc` 的 .ps1 被禁，改用 `.cmd` 直接调用
4. **async handler**：原来 wrap 只处理同步函数，async 返回 Promise 会被错误 json 化，需在 wrap 里识别 thenable
