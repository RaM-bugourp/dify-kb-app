# dify-kb-app 优化与对外 API 开放计划

> 版本：v0.2（计划稿，含范围收缩）
> 日期：2026-08-21
> 范围：内部知识库（PDF/PNG/JPG/术语表）统一管理 + 对接云 Dify 做检索 + **预留对外 API 供外部（如 PPT 生成服务）访问知识库调用信息**。

---

## 0. 现状评估（已通读代码）

### 已有基础（可复用，不动）
- 前后端分层清晰：`server/index.js`(路由) / `server/store.js`(数据访问，签名稳定) / `server/dify-bridge.js`(桥接)
- 图片上传已解决中文乱码（手写纯字节 multipart 解析），可直接复用到文档上传
- `dify-bridge.js` 接口签名已对齐 Dify 官方 REST，mock 模式建库→入库→检索已跑通
- 结构化表格（术语表）增删改查 + 单元格编辑已可用
- `store.js` 数据访问函数签名稳定，预留 MySQL 切换点

### 关键缺口（按严重度排序）
| # | 缺口 | 现状 | 影响 |
|---|---|---|---|
| G1 | **文档上传缺失** | `documents` 只有 seed 元数据，`/api/documents` 上传接口不存在 | PDF/MD 无法真正入库，链路断在起点 |
| G2 | **文件存储不统一** | 只有 `server/media/`（图片），文档原文件无处落盘 | 无法统一管理 PDF/图片 |
| G3 | **图片只能存原图** | 无 OCR / 多模态转文本能力 | 图片进不了 RAG 检索 |
| G4 | **术语表未接入检索** | 结构化表只供人看，无「表→文本」序列化 | 术语表无法喂给 Dify |
| G5 | **Dify 真实模式未验证** | `create_by_file` 未实现，检索无 rerank | 真实链路未闭环 |
| G6 | **无对外访问层** | 所有 `/api/*` 无鉴权、无版本、无契约文档 | 外部系统无法安全调用知识库 |
| G7 | **持久化仍是 JSON** | 单文件整体写，无原子写/备份 | 并发与可靠性弱 |

## 1. 目标链路定义（端到端，终点=对外 API）

```
文件(PDF/PNG/JPG) + 术语表(结构化表)
        │
        ▼
① 统一入库（原文件落盘 + 元数据入库）【后台管理】
        │
        ▼
② 内容解析（PDF→文本 / md→文本 / 图片→OCR/多模态描述 / 术语表→可检索文本）
        │
        ▼
③ 推送云 Dify 向量化（各类型文本各自入库）
        │
        ▼
④ 检索召回（hybrid_search + rerank，带 score 分段）
        │
        ▼
⑤ 对外 API 层（鉴权 + 版本化 + OpenAPI 契约）
        │
        ▼
⑥ 外部消费者（PPT 生成服务 / 其他系统）通过 API 拉取检索结果、术语表、文件
```

**定位重述**：本后台是「知识库的单一数据入口 + 对外服务出口」。PPT 生成等下游系统都是**外部消费者**，只通过对外 API 获取数据，不与后台耦合。

## 2. 分阶段计划（稳扎稳打，逐段验收）

### 阶段 0：可行性验证（POC，3~5 天）
**目标**：把链路上不确定环节逐一跑通，定选型；允许脚本/临时代码，不进 UI。

| 验证项 | 内容 | 通过标准 |
|---|---|---|
| V0-1 Dify 云连通 | 云 API key + base_url，跑通 建库→`create_by_file`(真实 PDF)→`retrieval` | 能返回命中分段 |
| V0-2 PDF 文本抽取 | 选型：`pdf-parse` / `unpdf` / `pdfjs-dist` | 中文 PDF 抽取质量可用 |
| V0-3 图片转文本 | OCR（Tesseract/云 OCR）vs 多模态 LLM（vision）二选一 | 中文图信息能转成可检索文本 |
| V0-4 对外 API 契约 | 定义对外接口清单 + 鉴权方式（见 §4 草案） | 外部能安全拉取检索结果/术语表/文件 |

**交付物**：《可行性验证报告》+ 选型结论 + 脚本级最小链路 demo（入库→检索→对外拉取）。

**需拍板（Gate 0）**：
1. 云 Dify 的 base_url / API key 归属（谁提供、存哪、是否走环境变量）
2. 图片转文本选 OCR 还是多模态 LLM（由 V0-3 结论定，若公司已有 OCR/vision 服务优先复用）
3. 对外 API 鉴权级别（内部单一 token？还是多 key 可管理？）

---

### 阶段 1：存储层统一 + 文档入库（地基）
**目标**：PDF / PNG / JPG / 术语表「真存、真管、真删」。

- 1.1 统一文件存储：新增 `server/files/`（文档原文件），`media/` 只存图片；元数据加 `kind: document | image`
- 1.2 文档上传接口：`POST /api/documents`（multipart，复用字节解析，支持 pdf/md/txt/docx）、`GET /api/documents/:id/download`、`DELETE /api/documents/:id`（连带删文件）
- 1.3 解析服务：`server/parser.js`，PDF/md/txt/docx → 文本，解析结果落盘缓存
- 1.4 术语表导出与同步：`GET /api/tables/:id/export`（json/csv）、`POST /api/tables/:id/sync-dify`（表→文本→推 Dify）
- 1.5 数据层加固：JSON 改「临时文件 + rename」原子写 + 备份快照；MySQL 迁移**暂缓**

**验收**：PDF/PNG/JPG 上传后能看、下载、删除；术语表能导出。

---

### 阶段 2：Dify 桥接层真实化
**目标**：云 Dify 全链路，含文件入库与高质量检索。

- 2.1 实现 `create_by_file` 真实文件入库（原文件直推 Dify，或推解析文本，按 V0 结论）
- 2.2 检索升级：`hybrid_search` + rerank（云 Dify 支持则启用），topK 可调，带 score 分段
- 2.3 图片入库策略：图片 → OCR/多模态描述文本 → 文本入 Dify（原图仍存本地，双存）
- 2.4 映射管理：分区↔Dify 知识库映射 UI 展示 + 同步/重建按钮 + 状态
- 2.5 错误与重试：索引失败状态、重试、结构化日志

**验收**：上传 PDF 后后台能看到 Dify 索引状态，检索测试台能召回内容。

---

### 阶段 3：前端管理界面完善
**目标**：一站式管理，操作闭环。

- 3.1 文档卡片：拖拽上传、下载、删除、索引状态、解析文本预览
- 3.2 图片增强：多选/拖拽上传；每张图展示「检索文本」并可手动修正
- 3.3 术语表：保留表格编辑，新增「同步到 Dify」按钮 + 导出
- 3.4 检索测试台：输入 query → 实时展示召回分段（来源 + score），验证召回质量
- 3.5 Dify 状态面板：每分区同步状态、文档数、最近同步时间

**验收**：全程 UI 完成「上传→索引→检索预览」。

---

### 阶段 4：对外 API 开放层 + 端到端测试
**目标**：提供安全、版本化、契约清晰的对外接口，外部系统可稳定调用。

- 4.1 鉴权：`Authorization: Bearer <API_KEY>`；后台可管理 API key（生成/吊销）
- 4.2 对外检索：`POST /api/v1/retrieval`（query + topK + 可选 scope 知识库/分区 → 带来源+score 分段）
- 4.3 结构化数据：`GET /api/v1/tables/:id/rows`（术语表等查询，支持过滤/分页）
- 4.4 文件访问：`GET /api/v1/documents/:id`（元数据+解析文本）、`GET /api/v1/files/:id/download`（原文件）
- 4.5 元数据：`GET /api/v1/tree`（知识库/分区结构）、`GET /api/v1/datasets`（列表）
- 4.6 OpenAPI 文档：`openapi.json` + 简易 Swagger 页，契约先行、版本化
- 4.7 端到端测试：真实文件（PDF+图片+术语表）跑通 入库→索引→检索→对外拉取，产出测试报告

**验收**：外部系统凭 token 能稳定拉取检索结果、术语表、文件；契约文档齐全。

## 3. 风险与建议

| 风险 | 应对 |
|---|---|
| 中文 PDF 抽取质量差 | 阶段 0 重点验证，必要时换解析库或加 OCR 兜底 |
| 图片信息丢失 | 图片只能转文本才可检索，务必「原图 + 文本」双存 |
| 云 Dify 网络/限流 | 阶段 0 验证连通与配额，检索加缓存与超时 |
| 术语表精确查询 Dify 弱 | 术语表保留结构化存储，对外提供精确查询接口 |
| 对外接口被滥用 | 鉴权 + 限流 + 访问日志，key 可吊销 |
| 范围失控 | 每阶段明确验收标准，未验证的重活不提前做 |

## 4. 对外 API 契约草案（阶段 0 V0-4 细化）

```
Base: /api/v1
Auth: Authorization: Bearer <API_KEY>

GET    /tree                          # 知识库/分区结构
GET    /datasets                      # 知识库列表
POST   /retrieval                     # 语义检索 {query, topK?, scope?} → {records[]}
GET    /tables/:id/rows               # 术语表精确查询 {filter?, page?}
GET    /documents/:id                 # 文档元数据 + 解析文本
GET    /files/:id/download            # 原文件下载
GET    /images/:id                    # 图片元数据 + 检索文本
GET    /health                        # 健康检查
```

- 返回结构统一 `{ code, data, error }`
- 检索结果带 `sourceType`（document/image/table）+ `score`，供下游（PPT 服务）追溯来源
- 契约走 OpenAPI，版本 `/v1` 稳定，后续破坏性变更走 `/v2`
